> 状态：需求定稿 + 技术选型拍板（2026-10-12）
> 关联仓库：`rag_helper`（客服智能体侧）。对接契约以该仓库 `evolution-plan.md` §5/§6 为准

## 0. 一句话

单商户自营的电子设备网购平台「一次买够」。Java 单体 + Vue 3 前后端分离，
经 gRPC 接入已有的 RAG 客服智能体。

## 1. 需求分析

### 1.1 背景与定位

| 项 | 定论 |
|---|---|
| 品类 | **电子设备** —— 与 `rag_helper/doc/` 的产品手册语料对应（打印机、路由器、笔记本、烫金机等） |
| 业务模式 | **多商户平台**：商家自助入驻 + 平台审核；商品归属店铺，跨店购物车按店拆单、分别支付；**不做佣金 / 分账 / 结算** |
| 项目定位 | **学习练手 / 简历项目**，不是真实运营；无真实支付、无高并发要求 |
| 差异化 | **接入已有的客服智能体**。这是本项目区别于普通电商 demo 的核心 |

智能客服当前范围**暂时定稿、将来再开发**：本期只做「产品问答 + 查订单 + 执行流可见」，
后续能力扩展走 `rag_helper` 的 subagent 机制，**不新增 Java 侧服务或端口**。

### 1.2 角色

| 角色 | 说明 |
|---|---|
| 顾客 | 浏览、下单、查订单、找客服；可申请成为商家 |
| 商家 | 入驻店铺、管理本店商品 / 订单 / 店铺券 / 评价 |
| 平台管理员 | 审核商户、管分类、全平台商品 / 订单 / 券 / 评价；**兼平台自营店客服**，在管理后台回复自营店消息 |
| 客服智能体 | 非人类。Java 是它的 gRPC **调用方**；将来它反向调 Java 的订单查询接口 |

**权限边界**：商家只能操作 `users.merchant_id` 对应的本店数据；平台管理员保留全平台监管权。

### 1.3 功能范围

#### 顾客侧

| 模块 | 功能点 | 优先级 |
|---|---|---|
| 账号 | 注册、登录、JWT 续期、改密码 | P0 |
| 收货地址 | 增删改查、设默认 | P0 |
| 商品浏览 | 分类树、列表、分页、关键词搜索、详情（图片/参数/库存） | P0 |
| 购物车 | 加购、改数量、勾选、删除、算总价 | P0 |
| 下单 | 结算页、生成订单、**扣库存**、**订单快照** | P0 |
| 支付 | **模拟支付**（点「支付成功」改状态），不接真实支付 | P0 |
| 订单 | 我的订单、详情、取消、确认收货 | P0 |
| 在线消息 | 顾客 ↔ 商家按店会话、文本/图片/商品卡/订单卡、未读与已读、离线留言 | P0 |
| 智能客服 | 页面内对话窗口，**流式**显示答复与执行流 | P0 |
| 售后 | 申请退款、退款进度 | P1 |

#### 管理侧

| 模块 | 功能点 | 优先级 |
|---|---|---|
| 商品管理 | 上下架、改价、改库存、传图、绑分类 | P0 |
| 订单管理 | 列表、筛选、发货（填单号）、改状态 | P0 |
| 用户管理 | 列表、禁用 | P1 |
| 知识库上传 | **不做** —— 上传是 agent 服务的管理端行为（evolution-plan §1 边界三） | 不做 |

#### 智能客服（差异化部分）

| 能力 | 说明 | 优先级 |
|---|---|---|
| 产品问答 | 问「这台打印机怎么装墨盒」→ agent 检索手册作答、带配图 | P0 |
| 查订单 | 问「我买的烫金机订单到哪了」→ agent 拿到订单数据 | P1 |
| 执行流可见 | agent 的调度步骤以灰色小字流式呈现 | P1 |

**P1 取舍（已拍板）**：时间不够时优先保「查订单 + 执行流可见」，
因为那是与智能体联动的特色；售后/用户管理可以砍。

### 1.4 核心流程与状态机

**下单主流程**：浏览 → 加购 → 结算 → 生成订单（扣库存）→ 模拟支付 → 管理员发货 → 顾客确认收货 → 完成

**订单状态机**：

```
待支付 ──支付──> 待发货 ──发货──> 待收货 ──确认收货──> 已完成
   │                 │
   └──超时/取消──> 已取消      └──申请退款──> 退款中 ──> 已退款
```

**必须做扎实的两点**：

1. **库存并发** —— 两人同时买最后一件不能超卖。方案：Redis 预扣 + 数据库乐观锁（版本号或
   `WHERE stock >= n`）。这是本项目最有价值的面试谈资
2. **状态流转合法性** —— 「已取消」的订单不能被发货。这类校验集中在订单服务里，
   不允许散落在各 Controller

### 1.5 领域模型

```
user ──< address
user ──< cart ──< cart_item >── product >── category
user ──< order ──< order_item
                   order >── payment（模拟）
```

**下单快照原则**：`order_item` 必须冗余存下单时的**商品名、单价、图片**。
商品后续改价，历史订单不能跟着变 —— 新手最常见的坑。

**主键约定**：`user.id` 用 `BIGINT` 自增，稳定不变。注入 gRPC metadata 时转成字符串
（evolution-plan §6 要求 Java 侧拍板此项，已定）。

### 1.6 非功能需求（按「简历项目」降级）

| 维度 | 要求 |
|---|---|
| 并发 | **不做**高并发。但库存扣减必须正确 |
| 安全 | 密码 BCrypt；JWT 鉴权；**越权校验**（A 不能看 B 的订单）—— 面试会问 |
| 金额 | 一律 `DECIMAL` / `BigDecimal`，**绝不用 double** |
| 可用性 | 单机，不做集群 |

### 1.7 明确不做

真实支付接入 · 秒杀/拼团 · 消息队列 · 微服务拆分 ·
移动端 App · 知识库上传

> **变更记录（2026-10-18）**：**优惠券已按用户要求解禁**，实现为满减券 + 领券中心 +
> 全场通用 + 取消/退款未过期自动退券（见 [implementation.md](implementation.md) §3.15）。
> 秒杀 / 拼团仍然不做。
>
> **变更记录（2026-10-19）**：**多商户已按用户要求解禁**，实现为商家入驻 + 平台审核 +
> 店铺商品 + 跨店拆单分别支付 + 平台/店铺券；**佣金、分账、提现/结算仍不做**。
> 详见 [implementation.md](implementation.md) §3.16。
>
> **变更记录（2026-10-19）**：新增**顾客 ↔ 商家在线聊天与私信留言**（M6 客服接入的前置），
> 实现在线会话、SSE 实时推送、未读/已读、商品与订单卡片；
> 管理员不参与聊天，商家不能主动私信。详见 [implementation.md](implementation.md) §3.17。

## 2. 技术选型

### 方案 A：全本地单体 + Docker Compose

- **技术栈**：Spring Boot 4.1.1 · MySQL 8 · Redis 7 · Spring Security + JWT ·
  Vue 3 + Vite + Element Plus。MySQL 与 Redis 由 Docker Compose 编排，
  应用跑宿主 JVM
- **为什么适合**：Docker 已在本机装好并运行中，`docker compose up -d` 即可拉起中间件，
  不装、不配、不管。零成本、零运维，出错一条命令全部重来
- **开发难度 / 维护成本**：最低。只需理解一个 Compose YAML
- **目标地区能否顺利使用**：完全不受影响，全部跑在本地
- **你得自己管的东西**：智能体的**服务端密钥**放 `.env`，**不得提交进 Git**。
  没有要打补丁的服务器
- **主要风险**：简历上没有可访问的线上地址；面试要么现场跑，要么录屏

### 方案 B：方案 A + Cloudflare Tunnel 公网演示

- **技术栈**：同 A，加 `cloudflared` 一条命令把本地端口映射成临时公网域名
- **为什么适合**：零成本拿到公网地址，面试官能直接点开
- **开发难度 / 维护成本**：低。一个可执行文件 + 一条命令
- **目标地区能否顺利使用**：Cloudflare 在大陆访问时好时坏，**需备录屏兜底**
- **你得自己管的东西**：同 A，密钥；另外**本机须保持开机**，关机即断
- **主要风险**：地址临时、每次重启会变；不能当长期「线上项目」

### 方案 C：方案 A + 云托管 7×24

- **技术栈**：同 A，部署到免费 PaaS。Render 有免费层（[官方定价页](https://render.com/pricing)
  确认仍有 Free，schema 标注 `price: 0`），但**免费实例 15 分钟无流量休眠**、冷启动数十秒。
  **Zeabur 慎用** —— [社区反馈免费共享集群即将收费](https://linux.do/t/topic/1639491/9)，
  官网已出现 "First 14 days free" 字样
- **为什么适合**：唯一能给出长期公网地址的零成本路径
- **开发难度 / 维护成本**：**高**。镜像构建、环境变量注入、免费数据库有效期、
  休眠唤醒 —— 对无部署经验者是真门槛
- **目标地区能否顺利使用**：Render 国内能访问但慢。要国内快只剩阿里云/腾讯云新用户试用
  （1–3 个月后收费），与「不想花钱」冲突
- **你得自己管的东西**：平台账号、密钥、数据库连接串、镜像构建配置。服务器补丁不用管
- **主要风险**：免费层政策说变就变（Zeabur 即是活例）；
  **Redis 几乎没有免费托管**，可能被迫降级方案

### 推荐：方案 A，做完按需加 B

**决定理由**：三条约束（零预算 / 未部署过 / 简历项目）中「未部署过」最硬。
方案 C 会把时间全吃在运维上，而本项目的真正价值在**电商领域建模**与
**gRPC 流式接入**。方案 A 让人立刻进入写业务代码的状态；需要公网演示时，
方案 B 是在 A 上**加一条命令**，不是推倒重来。

### 最终选型清单（2026-10-12 定稿）

| 层面 | 选型 | 备注 |
|---|---|---|
| 后端 | Spring Boot 4.1.1 + JDK 17 | 已就绪 |

### 中间件复用约定（硬约束）

本机 Docker 里已跑着**多个项目共用**的中间件，**本项目不另起容器，一律复用**：

| 中间件 | 复用容器 | 连接 | 本项目隔离方式 |
|---|---|---|---|
| MySQL | `mysql`（mysql:8.0，**当前 stopped**，需 `docker start mysql`） | `localhost:3306` | **独立 database：`its_mygo`** |
| Redis | `redis`（redis:7-alpine，运行中） | `localhost:6379` | **key 前缀 `its-mygo:`** |
| MinIO | `minio`（运行中，rag_helper 在用） | `localhost:9000`（Console `:9001`） | **独立 bucket：`its-mygo-product-images`** |

**命名约定**：现有共用容器**不改名、不新建**。但本项目**若**将来创建任何 Docker 资源
（卷、网络、容器），名字一律以 `its-my-go` 开头，**不依赖 Compose 从目录名推导的
默认前缀**（那会得到 `itsmygo_`）。

来源：`rag_helper/docker/redis-compose.yml` 的注释 —— 本机同时存在多个项目留下的卷
（`docker_mysql_data` / `docker_qdrant_data` / `docker_es_data`），
"从名字上看不出归属"是已经踩过的坑。

**Redis 写入约束**：共用容器以 `--maxmemory 256mb --maxmemory-policy volatile-lru` 启动，
该策略下**只有带 TTL 的 key 会被淘汰**。因此本项目写入 Redis 的所有 key
**必须带 TTL**，否则内存打满时写入会直接失败。

**凭据管理**：数据库口令走环境变量 / `.env`，**绝不提交进 Git** ——
本仓库是**公开仓库**，`.gitignore` 里要确保 `.env` 被排除。

## 3. 与智能体的对接契约（Java 侧必须遵守）

来自 `rag_helper/evolution-plan.md` §1/§5/§6，**不是本仓库能自行更改的**：

| 项 | 要求 |
|---|---|
| 拓扑 | Java **单体** + Agent 服务（单实例）。**不经网关、不上微服务** |
| 边界 | **浏览器只跟 Java 说话**；agent 服务只在内网、只允许本单体访问 |
| 接口 | gRPC `agent.v1.AgentService`：`Converse`（server streaming）/ `Stop` / `ListSessions` / `GetHistory` |
| 身份 | metadata 两条：`authorization: Bearer <服务端密钥>`、`x-user-id: <顾客ID>`。**注入前先剥离客户端同名值** |
| 超时 | deadline ≥ 180s（一轮墙钟预算）+ 余量；keepalive 代替应用层心跳 |
| run_id | 由 agent 服务自生成；平台存「平台请求 ↔ run_id」映射，**不透传当 thread_id** |
| 流式 | Java 收到事件流后转 **SSE** 推给浏览器 |

**proto 文件是唯一凭据**：`rag_helper/proto/agent.proto` 已定稿且
`option java_multiple_files = true`，Java 侧直接由它生成 stub。

**反向链路（P1）**：agent 的 `order-service` subagent 将来要调 Java 的订单查询接口。
Java 需**预留一个内网订单查询 API**，入参含 `user_id` + 订单号。

## 4. 分阶段路线

| 里程碑 | 参考工期 | 内容 | 可验收产物 |
|---|---|---|---|
| **M0 · 骨架** | 2–3 天 | 包结构、Docker Compose（MySQL+Redis）、统一响应/异常、Flyway 建表、**验证 Boot 4.1.1 生态兼容性** | `docker compose up -d` + 应用启动，能连库；兼容性结论落地 |
| **M1 · 账号体系** | 3–5 天 | 注册、登录、JWT、Spring Security 配置、地址 CRUD | Postman 注册登录拿 token，受保护接口可访问 |
| **M2 · 商品与分类** | 3–5 天 | 分类树、商品 CRUD（管理端）、列表/详情/搜索（顾客端） | 能通过接口上架商品并查询 |
| **M3 · 购物车 + 下单 + 库存** | 1 周 | 购物车、结算、订单生成、**库存扣减（Redis + 乐观锁）**、订单快照 | 完整下单链路跑通；**并发压测不超卖** |
| **M4 · 支付（模拟）+ 状态机 + 发货** | 3–5 天 | 模拟支付、订单状态机、管理端发货 | 订单全生命周期状态流转正确，非法流转被拒 |
| **M5 · 前端** | 1–2 周 | Vue 3 顾客端 + 管理端 | 浏览器完成完整购物流程 |
| **M6 · 客服接入** | 1 周 | 由 proto 生成 Java stub、gRPC 客户端、事件流 → SSE、前端对话窗口 | 浏览器里与 agent 对话，流式回复与执行流正常 |
| **M7 · 查订单环回**（P1） | 3–5 天 | Java 暴露内网订单查询接口给 agent | 「我买的烫金机订单到哪了」能正确作答 |

**贯穿**：每个里程碑结束跑一次受影响的回归；改动波及对接契约时同步本文。
