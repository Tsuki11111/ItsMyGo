## 0. 产品定位与背景

- **产品名**：一次买够（ItsMyGo），**多商户网购平台**（SaaS 化店铺，不做佣金 / 分账 / 结算）。
- **是什么**：Spring Boot 单体 + Vue 3 前后端分离的电商平台，覆盖商家自助入驻、店铺商品、
  跨店购物车按店拆单分别支付、平台监管；经 **gRPC** 接入外部 RAG 客服智能体「买小购」。
- **定位**：**学习练手 / 简历项目**，不是真实运营 —— 无真实支付；但**按高并发标准做**
  （用户 2026-10-15 明确要求：缓存、并发、一致性不因「没流量」降要求）。
- **与 rag_helper 的关系**：**浏览器只跟 Java 说话**；Java 是 agent 的 gRPC **调用方**；
  agent 只在内网、只允许本单体访问；需要实时数据时 agent 反向回调 Java 的内部接口。

## 1. 角色与使用场景

| 角色 | 关心什么 | 主要入口 |
|---|---|---|
| 顾客 | 逛商品、下单支付、查订单物流、找客服、评价与问大家 | 顾客端（Vue） |
| 商家 | 入驻、上架商品与 SKU、发货退款、店铺券、经营看板、店铺聊天 | 商家后台（/merchant/**） |
| 平台管理员 | 商户审核、分类、全平台商品 / 订单 / 券 / 评价、用户与审计、知识库与评测代理 | 管理后台（/admin/**） |
| 客服智能体（rag_helper） | 稳定的契约、可渲染的事件流、可确认的动作草稿、可信的身份票据 | gRPC + 内部 HTTP 回调 |

**核心使用场景**：

1. **交易闭环**：浏览 → 加购 →（按店拆单）结算 → 模拟支付 → 发货 → 收货 → 评价；
   取消 / 超时 / 退款会回滚库存与优惠券。
2. **多商户经营**：商家入驻审核、商品与 SKU 管理、订单处理、店铺券、经营看板。
3. **AI 客服**：产品问答、查订单物流、导购与商品卡、智能下单 / 退款草稿、
   催发货 / 催退款、知识库导入、管理端 LLM-as-Judge 评测。
4. **商品社区**：确认收货后评分评价（评分分布 / 星级筛选）；问大家（提问 + 买家回答）。
5. **平台治理**：数据概览、订单筛选与 CSV 导出、用户禁用、操作审计、管理员邀请审批。
6. **售后**：买家对已付款订单发起**仅退款 / 退货退款**（可按商品部分退），商家或平台审核，
   商家超时自动处理；买家可撤销售后、可填退货单号；进度以时间线展示。

| 能力 | Java 做什么 |

### 2.5 售后与退货（M30，2026-11-05 定）

**为什么单独立「售后单」**：退款只是订单状态的一个分支，撑不起「部分退款 / 退货 / 多次售后 /
处理记录」；一个订单可能需要多条售后（不同商品、不同时间），订单状态无法表达多路并发。

**售后类型**：

| 类型 | 适用订单状态 | 流程 |
|---|---|---|
| `REFUND_ONLY`（仅退款） | `PAID` / `SHIPPED` / `COMPLETED` | 申请 → 审核通过 → 直接退款 |
| `RETURN_REFUND`（退货退款） | `SHIPPED` / `COMPLETED`（已发货才谈退货） | 申请 → 审核通过 → 买家寄回填单号 → 商家确认收货 → 退款 |

**售后状态机**（`after_sales.status`）：

```
PENDING_REVIEW ──同意(仅退款)──────────────> REFUNDED
      │    └────同意(退货退款)──> WAITING_RETURN ──买家填单号──> RETURN_SHIPPED ──商家确认收货──> REFUNDED
      ├────驳回（必填理由）────────────> REJECTED（可再次申请）
      └────买家撤销───────────────> CANCELLED
```

- **部分退款**：一个售后单可包含多个订单项、每项可退部分数量；金额按订单项单价 × 数量，
  **优惠按订单维度等比分摊**（尾差归最后一次退款）；同一订单项「进行中 + 已退款」数量之和不得超过购买数量。
- **券的退回口径**：**只有订单全部商品都退款完成**时才退回优惠券（部分退款不退券）；
  平台无运费字段，不涉及运费分摊。
- **库存回补**：按售后单的订单项逐项回补（SKU 条件更新 + Redis 计数器 + 商品汇总），**幂等**。
- **商家处理时限**：默认 **48 小时**未审核 → 自动同意（可配置）；退货单寄出后
  **7 天**商家未确认收货 → 自动确认并退款（可配置）。平台可随时介入处理。
- **凭证**：申请可上传最多 3 张图片（复用 MinIO，`aftersales/` 前缀）。
- **原因字典**：平台维护的售后原因（编码 + 名称 + 排序 + 启用状态），申请时必选。
- **三端页面**：顾客端「申请售后」+「我的售后」+ 售后详情时间线；商家端售后列表 / 处理；
  管理端全平台售后列表 / 介入 / 原因字典维护。
- **统计**：商家看板与平台概览增加「售后中 / 待商家处理」计数（按售后状态聚合，不做趋势图）。
- **与旧退款的关系**：现有 `/api/orders/{id}/refund` 整单退款接口**保留**（历史数据与既有测试、
  AI 客服「催退款」仍依赖 `REFUNDING` 状态）；**新入口一律走售后单**，后续再统一下线旧接口。
  ⚠️ 因此 AI 客服的「催退款」本期**只对旧整单退款生效**，新售后单的催办走商家端列表，P3 再统一。

**本版明确不做**：换货、售后凭证视频、退货运费规则、真实快递对接、售后站内通知、
AI 客服「查售后进度 / 代申请售后」（都列在 P3 或按需区）。

### 2.6 下单异步补账（M31 / D1，2026-11-05 定）

**背景**：下单主链路目前是一个同步事务（Redis 预扣 + DB 扣库存 + 订单/明细/券落库 + 清购物车 +
发超时消息）。用户确认要引入 RabbitMQ，把「占位订单之后的补账动作」移出请求路径，
即 **D1：半同步占位 + 异步补账**（不是纯异步落库）。

**目标**：缩短下单响应时间，同时保留「订单号立即可查」——不引入纯异步方案的“读己所写消失”。

**状态机（新增 2 个状态）**：

```
CREATING ──补账成功──> PENDING_PAYMENT → 后续与现有交易状态机一致
    │
    ├──补账失败 / 超时──> CREATE_FAILED（终态，可重新下单）
    └──（不允许从 CREATING 支付 / 取消 / 退款）
```

**同步段（下单请求内，事务）**：
1. 提交令牌、地址 / 商品 / SKU / 店铺 / 券**校验**（与现状一致）；
2. Redis 预扣（防超卖的闸门，与现状一致）；
3. INSERT 占位订单（`CREATING`，含订单号/金额/收货快照）+ INSERT 订单明细（快照）；
4. 事务提交后发 MQ「订单已创建」事件；返回 `orderId` 与“创建中”状态。

**异步段（消费端，按事件补账）**：
1. DB 条件扣库存（`WHERE stock >= ?`，最终真相）+ 商品汇总；
2. 优惠券占用（条件更新，失败即整条补账失败）；
3. 清空本次下单的购物车行（按事件里的行 ID 快照，避免误删后来加入的商品）；
4. 订单状态 `CREATING → PENDING_PAYMENT`（CAS）；
5. 事务提交后为每张订单发「超时关单」延迟消息（与现有 D11 一致）。

**失败与兜底**：
- 补账事务失败 → 事务回滚 + **Redis 预扣回补** + **券回滚** + 订单置 `CREATE_FAILED`（写失败原因）；
- 事件重投 / 重复消费按订单状态幂等（非 `CREATING` 直接跳过）；
- **CREATING 超时扫描**（默认 2 分钟，可配）：未完成的订单重新投递事件（最多 N 次），仍失败则走失败补偿；
- MQ 不可用或关闭时，走**同步补账降级模式**（`async=false`），行为与旧链路等价（测试与本地无 MQ 环境用）。

**前端**：
- 结算结果页 / 订单详情在 `CREATING` 时显示“订单创建中”，**轮询直到 `PENDING_PAYMENT` 或 `CREATE_FAILED`**；
- `CREATING` 期间支付按钮禁用；`CREATE_FAILED` 提示原因并引导重新下单；
- 订单列表展示新状态中文名（后端下发）。

**明确不做**：
- 纯异步（不落占位订单）——读己所写消失、支付门槛无法处理；
- Redis+DB 强一致 / 跨库分布式事务 / 事务 Outbox；
- 把支付、发货、售后链路也异步化。

**自评审（2026-11-05）**：
1. 目标可验证：CREATING 可查、补账成功可支付、失败可回滚、超时可兜底、降级模式旧行为不回归；
2. 范围收敛：只改订单创建链路，支付/发货/售后/客服契约不动（rag_helper 无需改）；
3. 边界明确：不承诺强一致；MQ 仍是至少一次投递，靠状态 CAS + 幂等消费；
4. 风险已确认：异步后“受理成功但最终失败”的窗口变长（用状态可见 + 自动补偿缓解），
   压测收益有限（下单不是当前瓶颈），主要价值是链路解耦与 MQ 实践；
5. 与既有决策不冲突：D4（DB 条件更新兜底）、D6（提交令牌）、D9（拆单事务）、D11（超时关单）保持。

### 2.8 站内通知（商家端 / 平台管理端，2026-11-08 定）

**场景**：商家/管理员在后台时，需要及时看到与自己相关的业务事件，不必一直盯聊天页或手动刷新列表。

**v1 通知类型**：

| 类型 | 接收人 | 触发 |
|---|---|---|
| `ORDER_PAID` 新订单待发货 | 店铺负责人；平台自营店 → 全部管理员 | 订单支付成功（事务提交后） |
| `AFTER_SALE_APPLIED` 新售后申请 | 店铺负责人 | 顾客提交售后 |
| `AFTER_SALE_RESULT` 售后处理结果 | 店铺负责人 | 平台同意/确认收货退款、超时自动处理 |
| `MERCHANT_APPLY` 商家入驻待审核 | 全部管理员 | 提交/重新提交入驻申请 |
| `AGENT_EVAL_DONE` 智能体评测完成 | 全部管理员 | 评测任务到终态（completed / failed / stopped） |

**交互**：商家端、平台管理端顶栏「铃铛」+ 未读角标；下拉最近 20 条，点击跳转对应页面，
支持「全部已读」。未读数 **30s 可见轮询**（复用角标轮询机制，不新增常驻 SSE）。

**存储**：`notifications` 表（Flyway **V35**），`biz_key` 幂等去重（同一接收人同事件只插一次）；
通知不设过期，保留本版全部。

**范围外**：浏览器系统通知 / 声音、短信 / 邮件 / IM webhook、按用户配置通知偏好、顾客端通知。
**验收**：通知列表/未读数/已读接口可用；入驻申请触发管理员通知、订单支付触发商家通知；
单测覆盖幂等与已读。

## 3. 非功能需求（NFR）

### 3.1 并发与一致性（本项目重点）

- **库存不超卖**：Redis Lua 原子预扣（挡流量）+ 数据库 `UPDATE ... WHERE stock >= ?`（最终真相）；
  禁止「先 select 再 update」的丢更新写法。
- **防重复下单**：一次性提交令牌（`GET /api/orders/token` + 原子消费）。
- **缓存三防**：穿透用布隆过滤器、击穿用互斥锁加载、雪崩用 TTL 抖动；缓存与数据库**不在同一事务**，
  回补 Redis 只在确实存在键时做。
- **拆单一致性**：一次结算生成 N 个订单在**一个事务**内；Redis 预扣与令牌归还在
  `afterCompletion(ROLLED_BACK)` 回补，且用标记防重复回补。
- **限流**：注解式（AOP + Redis 固定窗口）按 IP / 用户维度，`itsmygo.ratelimit.enabled=false`
  可一键关闭止血。
- **状态流转原子**：条件更新（CAS），并发支付 / 退款只成功一次。

### 3.2 安全

- 密码 BCrypt；JWT（HS256）只携带 userId，**role / merchantId 每次按数据库实时推导**
  （60 秒缓存 + 变更 evict），角色变更需重新登录才能看到新权限。
- **越权一律返回 404**（不泄露数据存在性）；管理端 / 商家端路径分别 `hasRole("ADMIN")` /
  `hasRole("MERCHANT")`。
- `/internal/agent/**` 是 `permitAll`，**唯一凭证是每轮票据**；只在内网暴露。
- 凭据只走环境变量 / `.env`，仓库公开，**绝不提交密钥**。

### 3.3 数据与金额

- 金额一律 `DECIMAL` / `BigDecimal`，绝不用 double。
- **订单快照**：`order_items` 冗余商品名 / 单价 / 图片，`orders` 冗余收货人 / 电话 / 地址；
  商品改价、用户改地址不影响历史订单（空图可兜底，其余快照字段不兜底）。
- 时间比较让两边来自同一时钟源（超时判断用数据库 `NOW()`）。

### 3.4 可观测性与可运维性

- 日志带 `traceId` / `userId`（MDC），prod profile 输出 JSON 文件保留 14 天。
- 管理端写操作 AOP 审计（操作人 / 动作 / 目标 / 结果 / IP / UA / traceId），审计失败不影响业务。
- `./deploy.sh` 一键全栈；`rag_helper/deploy.sh joint` 联合部署；生产（演示）环境为内网 VM。

### 3.5 质量门禁

- 后端自动化测试 **322 条**（本地；CI 318 条，跳过 4 条依赖 MinIO 的用例）；
- 前端无自动化测试，靠手工走查 + `npm run build`/`vue-tsc`；
- 压测基线与复现方法见 [HANDOFF.md](../HANDOFF.md) §4.8；
- 已知但未处理的高并发问题清单在 [HANDOFF.md](../HANDOFF.md) §5 末尾，动手前先看。

## 4. 平台对接需求与前提（Java ↔ agent）

> 权威是 `rag_helper/proto/agent.proto`（字段源码）+ `rag_helper/docs/architecture.md` §4
> （契约说明）+ `rag_helper/docs/requirements.md` §4（对接前提）。
> 本仓库**不能自行更改对接契约** —— 要改先跟用户确认，并同步改 rag_helper。

| 项 | 定论（Java 侧） |
|---|---|
| 拓扑 | Java **单体**（单实例）+ agent 服务（单实例）；不经网关、不上微服务 |
| 边界 | **浏览器只跟 Java 说话**；agent 只在内网、只允许本单体访问 |
| 接口 | gRPC `agent.v1.AgentService`：`Converse`（server streaming）/ `Stop` / `ListSessions` / `GetHistory` |
| 身份 | metadata：`authorization: Bearer <服务端密钥>` + `x-user-id: <顾客ID>`；**注入前先剥离客户端同名 metadata**；另有每轮 `x-agent-tool-ticket` |
| 顾客 ID | MySQL `BIGINT` 自增，注入 metadata 时**转字符串** |
| 超时 | Java 侧 `AGENT_GRPC_DEADLINE_SECONDS=240`；keepalive 300s 代替应用层心跳 |
| 票据 | Java 每轮 `Converse` 签发（Redis 10 分钟，**必须 ≥ deadline**）；回调时经 `X-Agent-Ticket` 带回 |
| run_id | 由 agent 生成；Java 存「请求 ↔ run_id」映射，**不透传当 thread_id** |
| 流式 | 事件流 → SSE 推浏览器；`final` 之后还可能来 `usage`，必须读到 EOF 再发 done |
| 反向链路 | agent → Java 内网 HTTP + JSON：`/internal/agent/orders/query`、`/internal/agent/catalog/products\|all\|categories\|addresses`、`/internal/agent/actions/order\|refund\|urge-shipment\|urge-refund`（及 `/send`） |
| 写操作 | agent 只 **prepare**；Java 落 `PENDING_CONFIRM` 快照；用户确认后 **Java 执行**；确认接口只收 `actionNo` |
| 商品卡 | proto 的 `FinalEvent` / `HistoryMessage` 增加 `ProductCard`；卡片内容以 Java 为准 |
| 导入 / 评测 | 继续 **HTTP + JSON**，由 Java 管理端带访问密钥代理，**不新增 gRPC RPC** |
| Java 侧限流 | 客服对话 10 次/60s/用户、动作确认 10 次/60s、评测启动 3 次/60s |
| 契约铁律 | **只加字段不删改**（旧消息返回空列表）；改 proto 双端同步；`option java_multiple_files = true` |
| 隔离边界 | 知识库全平台共享；需要按人隔离的只有会话 / 账本 / 运行记录 |

## 5. 验收标准

**已完成形态的验收口径**（逐项都有实测记录，见 [HANDOFF.md](../HANDOFF.md) §6）：

1. 交易闭环在浏览器走通：浏览 → 加购 → 按店拆单 → 支付 → 发货 → 收货 → 评价；
   取消 / 超时 / 退款回滚库存与券。
2. 并发正确：10 并发抢 5 件库存**恰好 5 单成功**；同一订单 5 并发支付**只产生 1 条流水**。
3. 压测基线留下可复现数据：商品列表 / 详情 2600–3500 QPS，分类 / 令牌 / 布隆 7000+ QPS，
   全程零失败、Full GC 0 次。
4. AI 客服四类场景走真实链路：产品问答 / 导购 / 查订单 / 动作草稿确认；
   执行流与卡片在浏览器可渲染。
5. 一键部署：`./deploy.sh` 起全栈，`rag_helper/deploy.sh joint` 联合启动，
   两端 `/api/health` 与 agent `/health` 均通过。
6. 测试与文档：后端 322 条全绿（CI 318）；implementation / HANDOFF / README 同步。
7. **售后**：整单与部分退款金额正确（优惠按比例分摊、尾差不丢），退货退款全链路可走通，
   同一订单项不能重复退超量，商家超时自动处理生效，越权一律 404。
8. **下单异步补账（M31）**（已实现，2026-11-06；单测 + 真实 RabbitMQ 端到端均通过，验收见 HANDOFF §6）：
   - 下单返回时订单可查，状态为「创建中」；
   - 补账成功后自动转「待支付」，随后可支付 / 取消，行为与旧链路一致；
   - 模拟补账失败（如 DB 库存为 0）→ 订单转「创建失败」、Redis 预扣回补、券可用、原因可见；
   - 重复事件 / 重复消费不产生重复扣减或重复退款；
   - 降级模式（`async=false`）下整条链路与旧同步链路行为一致；
   - 创建中订单**不能支付**，`CREATING` 超时会被扫描兜底处理。

## 6. 范围外与按需区

**明确不做**：真实支付接入、佣金 / 分账 / 结算、秒杀 / 拼团、**换货**（售后只做仅退款 +
退货退款）、账号自助注销、移动端 App、微服务拆分。

**按需区（将来需要时不再重新论证）**：

- **多实例**：SSE 在线状态与 `@Scheduled` 布隆过滤 / 订单扫描都按单实例写；
  扩容需要 Redis Pub/Sub 或粘性会话。
- **订单号冲突重试**：目前 `yyyyMMddHHmmss` + 6 位随机，撞唯一索引直接报错而非重试。
- **连接池**：HikariCP 默认 10 连接，压测前需调大。
- **智能体评测 / 知识库导入**：属于 rag_helper 的管理端行为，Java 只代理，不建独立服务。
- **售后 P3**：AI 客服查售后进度 / 代申请售后（需新增内部接口与 rag_helper 工具，跨仓库契约变更）、
  售后站内通知、售后凭证视频、真实快递对接、换货。

## 9. 术语与命名约定

| 术语 | 含义 |
|---|---|
| 顾客 / 商家 / 平台管理员 | 三种有效角色（`CUSTOMER` / `MERCHANT` / `ADMIN`）；商家角色由店铺 `ACTIVE` 状态决定 |
| 商户 / 店铺 | `merchants` 行；默认商户 id=1 为平台自营店 |
| 拆单 | 跨店结算按店拆成 N 个订单，各自支付 |
| 提交令牌 | 下单防重复的一次性令牌（Redis，原子消费） |
| 草稿 / 动作 | AI 客服的「提议」形态：`agent_actions` + `PENDING_CONFIRM`，用户确认后由 Java 执行 |
| 内部接口 | `/internal/agent/**`，agent 回调 Java 专用，不对外 |
| 快照 | 订单 / 动作里冻结的历史数据，不随商品或地址变化 |
| 售后单 | `after_sales` 行：一次售后诉求的独立生命周期（类型 / 状态 / 金额 / 时间线 / 凭证） |
| 仅退款 / 退货退款 | 售后类型：`REFUND_ONLY`（不退货直接退）/ `RETURN_REFUND`（买家寄回后商家确认再退） |
| 部分退款 | 只退订单里的部分订单项 / 部分数量；金额按项单价计、优惠按订单等比分摊 |
| `its-my-go` | 本项目所有外部资源（Docker、MinIO bucket、Redis key 前缀）的命名前缀 |
